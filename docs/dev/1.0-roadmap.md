# Audplexus 1.0 Roadmap

This roadmap describes the work needed to move Audplexus from a capable self-hosted alpha/beta project into a stable 1.0 release. It is written to emphasize release readiness, not just feature completeness.

## 1.0 definition

Audplexus 1.0 should mean:

- the installation path is straightforward and documented
- the first-run and recovery flow is understandable to a technically capable user
- the core loop is reliable: Audible sync, download, metadata organization, and delivery to destinations
- failure states are visible, actionable, and recoverable
- upgrade and migration paths are safe and tested
- the application is stable enough to run as a daily tool without frequent manual intervention

This is not a “everything is perfect” milestone. It is a “the rough edges are predictable and recoverable” milestone.

## Guiding principles

1. Reliability before breadth.
   - Fix the failure modes that cause the most user pain before adding new features.
2. Observability before scale.
   - If a user cannot tell what failed and why, the system is not 1.0 ready.
3. Safe defaults over clever defaults.
   - Default behavior should protect user data and avoid hidden surprises.
4. Upgrade safety is a product feature.
   - Schema changes, config shifts, and account reauth must be tested as real operational workflows.
5. Focus on the real app loop.
   - The core value is Audible library ingestion -> local storage -> destination delivery.

## Release order

The phases below are intentionally ordered from the most important risks to the least. This is the sequence I would use for a real 1.0 release plan.

---

## Phase 1: Release baseline and operational guardrails

### Goal

Create the baseline needed to safely ship a production-grade self-hosted app.

### Why this comes first

Without operational guardrails, a stable release process creates more risk than value. The project already has Docker packaging and CI, but release readiness still needs the discipline around failure handling, telemetry, and upgrade safety.

### Work items

- finalize versioning and release policy for Docker and GitHub releases
- define the supported runtime matrix and dependencies clearly
- document install and upgrade steps for the main deployment methods
- create a “known issues / limitations” page for users and maintainers
- define a bug report template and required diagnostics bundle
- establish a maintenance policy for supported media-server backends and database versions
- add a release checklist that includes migration/testing verification before tagging

### Exit criteria

- a fresh install path works without guesswork
- an upgrade path is documented and tested
- maintainers know exactly what is in scope for the current release
- a user can file a useful bug report without code archaeology

---

## Phase 2: Data integrity and resilience

### Goal

Make the app safe under partial failures, retries, and interrupted work.

### Why this comes next

Almost every 1.0 blocker in a library downloader is caused by state corruption, incomplete jobs, or retries that are not idempotent. This is the highest-risk layer for user trust.

### Work items

- make sync and download jobs idempotent where possible
- ensure partial downloads are resumed or cleaned up safely
- define clear handling for interrupted library syncs and failed book conversions
- add durable state tracking for queue items, active downloads, and retries
- verify that re-running a failed job does not duplicate content or create inconsistent metadata
- review filesystem safety for destination writes and temporary directories
- ensure DB migrations are reversible or at least clearly safe for upgrades
- add warnings for mismatched or inconsistent library state

### Acceptance criteria

- a failed download can be retried without corrupt state
- interrupted jobs do not leave half-written or misidentified book records
- repeated syncs are safe and converge to the same result
- migration and upgrade behavior is validated with test or staging runs

---

## Phase 3: Core workflow hardening

### Goal

Make the central Audplexus workflow dependable in everyday use.

### Scope

This includes:

- Audible account connectivity and token refresh
- library scan and sync correctness
- ongoing book download flow
- metadata enrichment and organizer output
- destination handoff to Plex, Jellyfin, Emby, or Audiobookshelf

### Work items

- make account auth refresh and reauth flows reliable
- reduce false positives and missed matches during library sync
- harden the organizer for edge cases: duplicates, title collisions, missing metadata, cover/author formatting quirks
- add better validation of destination output paths
- define expected behavior when a book is already present or partially present
- ensure destination sync is visible and auditable from the UI
- add clear “success / skipped / failed / retryable” states for each book or job item

### Acceptance criteria

- a normal user can keep a library in sync without manual cleanup for weeks
- book naming and organization are stable and not surprising
- destination handoff is consistent across supported backends
- repeated runs converge to a clean state instead of generating drift

---

## Phase 4: Recovery, diagnostics, and supportability

### Goal

Make the application diagnosable without reading source code.

### Why this matters for 1.0

A self-hosted app only feels stable when a user can recover from a failure without a maintainer jump-start.

### Work items

- improve diagnostics screens and logs for sync/download failures
- centralize the most important status information in the UI
- add context-rich job logs for matches, file actions, and backend calls
- provide summary-level error reporting that surfaces actionable next steps
- include support for exported diagnostic bundles or debug snapshots
- document common failure modes with fixes and escalation paths
- make logs understandable for both normal users and maintainers

### Acceptance criteria

- users can tell exactly which book, destination, or sync step failed
- support docs cover the common errors without requiring source code reading
- a maintainer can debug a production issue from the exported state and logs

---

## Phase 5: Setup, UX, and first-run confidence

### Goal

Turn the product from “works once configured” into “feels safe to set up.”

### Work items

- simplify the first-run experience for new users
- validate required directories, permissions, and config before key actions begin
- add clear onboarding or setup warnings for missing credentials or destination config
- make Settings and status pages easier to understand
- reduce hidden configuration complexity where possible
- define sane defaults for scheduling, storage, and cleanup behavior
- make admin/bootstrap auth flow explicit and safe

### Acceptance criteria

- a new user can complete setup without accidental misconfiguration
- missing config is surfaced early and clearly
- the UI gives confidence that the app is healthy before it is asked to do work

---

## Phase 6: Security and trust hardening

### Goal

Reduce the operational risk of running the app on a network-facing system.

### Work items

- review admin auth and bootstrap auth flows
- document secure deployment patterns for reverse proxy and container use
- review secret storage and config handling
- lock down defaults for exposed routes and authentication boundaries
- verify session and token handling is safe and predictable
- assess rate limiting and abuse protections for HTTP endpoints
- validate that app behavior stays sane when credentials or remote services are unavailable

### Acceptance criteria

- deployment docs show the secure path for self-hosted use
- secret handling is explicit and not accidental
- the app does not create surprising trust or auth gaps in normal operation

---

## Phase 7: Performance and scale validation

### Goal

Confirm the app remains usable for real libraries, not just small test datasets.

### Work items

- measure sync throughput with larger libraries
- validate scheduler behavior under repeated scans and active downloads
- review database growth and cleanup strategy
- assess the cost of metadata and organizer operations across large numbers of books
- test concurrency behavior for parallel queues and destinations
- identify slow or pathological paths and document expected limits

### Acceptance criteria

- large libraries are manageable without obvious queue starvation or resource exhaustion
- performance profile is documented for expected workloads
- some hard limits are known and made explicit rather than hidden

---

## Phase 8: Release candidate and launch gate

### Goal

Ship only when the project is stable enough to trust in real life.

### Required release gate

Before tagging 1.0, the project should pass all of the following:

- full test suite passes on main supported environment
- upgrade path is tested for at least the most common deployment style
- core user flow is validated end-to-end: setup -> sync -> organize -> destination delivery
- failure/retry scenarios are tested and documented
- admin and auth setup is reviewed and hardened
- known limitations are explicitly documented
- release notes describe what is covered and what is not

### Final sign-off checklist

- install is obvious
- first-run is understandable
- core workflows are reliable
- failures are diagnosable
- upgrades are safe
- docs match reality
- the project is stable enough for daily use

If every item above is in place, the project is ready for 1.0. If not, it is still a strong beta or RC release.

---

## Suggested release sequence

1. Operational baseline and supportability
2. Data integrity and retry safety
3. Core workflow stability
4. Diagnostics and recovery paths
5. Setup and first-run UX
6. Security hardening
7. Scale and performance validation
8. Release candidate and launch gate

This order keeps the biggest trust risks first and ensures that the final release is less about “new features” and more about confidence.

## Practical note

The biggest difference between a mature beta and a 1.0 release is not the number of features; it is whether the product remains understandable and recoverable when something goes wrong. That should be the final test for this project.
